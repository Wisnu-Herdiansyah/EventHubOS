# ADR-0042: Asset library (images)

- Status: accepted
- Date: 2026-11-11
- Builds on: ADR-0020 (microsite pages), ADR-0021 (public sites), ADR-0040 (speakers)
- Threat model: T68, T69, T70
- Open decisions: the production object store waits for D1 (cloud platform) and D7 (region)

## Decision

Each organization has an **image library**. Images are uploaded once and used on event pages.
Speaker photos are the first use.

### Storage behind a port

Image bytes live behind the `ObjectStore` port (`put`, `get`, `delete`; deleting a missing
object succeeds). A shared contract test covers every adapter.

| Adapter           | Use                                                  | Remote environments |
| ----------------- | ---------------------------------------------------- | ------------------- |
| `local_directory` | Local development and e2e (shared by API and worker) | Refused             |
| `in_memory`       | Integration tests                                    | Refused             |
| (provider)        | Not built: needs D1 and D7                           | —                   |

- The setting is `OBJECT_STORE` (and `OBJECT_STORE_DIR`) on both the API and the worker.
- It is optional. Without it, uploads and image bytes answer `503 storage_unavailable`, the
  library says uploads are off, and pages keep working with initials.
- In staging and production the local adapters fail configuration, so no remote server keeps
  files on one machine's disk.
- Keys are generated by the server, never taken from a client:
  `organizations/{org}/assets/{asset}/{large|small}.webp`. Adapters also refuse any key that
  could escape its prefix.

### Uploads are re-encoded, never stored as sent

`POST /v1/organizations/:org/assets` takes `asset.manage`. The file arrives base64-encoded in
JSON, so the route keeps the usual contract, validation and idempotency. That route alone allows
an 11 MB body.

1. **Format from the bytes.** Only JPEG, PNG and WebP signatures are accepted. SVG (which can
   carry script), GIF, HEIC, PDF and everything else is refused before any decoder sees it.
2. **Strict decode.** At most 8 MB and 50 megapixels; truncated or corrupt data is refused; the
   decoder must agree with the signature.
3. **Re-encode** with libvips (`sharp`):
   - camera orientation is applied;
   - all metadata (EXIF including GPS location, XMP, comments) is dropped;
   - animated images keep their first frame;
   - two WebP renditions are stored: large (fits 2400 px) and small (fits 480 px).

Order of work:

- A short transaction checks the permission and the library size first.
- Processing happens outside any database transaction.
- The write transaction then claims the idempotency key, stores the bytes, inserts the row, and
  writes the audit and outbox records.
- If the commit fails after the bytes are stored, an unreferenced object is left behind. A
  library row never points at missing bytes. (Orphan cleanup waits for retention work, D9.)

**Library limit:** 500 images per organization. It is checked before processing and again under
a per-organization advisory lock, so concurrent uploads cannot pass it.

### Who sees what

| Action                              | Permission                                                                |
| ----------------------------------- | ------------------------------------------------------------------------- |
| List, view bytes (small or large)   | `event.read` (everyone who can preview pages)                             |
| Upload, rename, change text, delete | `asset.manage` (Owners, Admins, Event managers, Content editors)          |
| Public bytes                        | Only while the current published revision of a public page uses the image |

- Assets are tenant-owned rows under forced RLS. Another organization's image is not found, by
  URL or on a page.
- The admin serves images through its own authenticated proxy (`/orgs/:org/images/:id/:variant`,
  `private, max-age=300`). Drafts can show photos without anything becoming public.
- The public site serves `/images/:id/:variant.webp` on the organization's own host. It asks
  `public_asset(handle, id)`, a definer function that applies the same rules as
  `public_event_page`: an active organization, and a public or unlisted event that is
  published, live or ended. On top of that, some string in the current published revision's
  sections must equal the image ID. Image IDs are random UUIDs, so nothing else matches, and
  future image fields are covered without a new migration. **A draft never makes an image
  public**, and an unused library image is never public.
- Image responses: `content-type: image/webp`, `nosniff`, `content-disposition: inline`, and
  `content-security-policy: default-src 'none'; sandbox`. Public caching is
  `public, max-age=300`, so unpublishing stops serving within minutes (CDN rules: D1).

### Pages refer to images by ID

- **Speakers v3** = v2 plus `photoAssetId` (an image ID or null). This is a new version, as
  ADR-0020 requires.
- Drafts with v1 or v2 speakers open upgraded to v3 in the editor, with no photos.
- Saving a draft checks that every image it uses is a live image of this organization, and
  holds `FOR SHARE` row locks on those images until commit.
- Publishing re-checks the same.
- Speaker photos are decorative (`alt=""`): the name is right below. The library still keeps a
  text alternative per image for future uses where an image carries meaning.

### Deleting

`POST …/assets/:id/delete` (`asset.manage`):

- It locks the image row, then refuses (`409 asset_in_use`, naming up to 5 events) while any
  draft or current published revision uses the image. The row lock and the draft save's
  `FOR SHARE` lock mean a delete and a save that uses the image can never both succeed
  (race-tested).
- Otherwise the row is soft-deleted (kept for the audit trail), and an `asset.deleted` outbox
  event lets the worker remove both renditions. The worker checks that the key belongs to the
  event's own organization and asset.

**Audit:** uploads, edits and deletes are audited with sizes and field names only, never the
image name or text.

### Admin

- **Images** in the organization sidebar (for `asset.manage`): upload (file, name, text
  alternative), a grid with size and dimensions, edit, and delete with the in-use explanation.
- **Page editor:** each speaker has a photo picker listing the library; the preview shows the
  photo at once.
- Uploads go through a server action. Its body limit is raised to 9 MB for this.

## Alternatives

- **Images from external URLs.** No storage needed, but every visitor's browser would contact
  third parties (tracking), the site CSP would have to allow other origins, and links rot.
  Rejected in ADR-0040; still rejected.
- **Store bytes in PostgreSQL.** Simple and transactional, but it bloats backups and WAL, and
  serves large blobs through the database. Object storage is the architecture's choice; the
  port keeps that open until D1/D7.
- **Store the upload as sent, or only strip EXIF.** Keeping the original keeps every parser risk
  and every piece of metadata. Re-encoding removes both and gives predictable sizes.
- **Direct-to-bucket signed uploads.** Better for large files, but provider-specific (D1), and
  the bytes would reach storage before validation. Revisit with the provider.
- **Make every library image public by unguessable URL.** Simpler serving, but uploads (for
  example an unannounced speaker) would leak before publication, against ADR-0020.

## Consequences

- One new native dependency: `sharp` (libvips) in the API, using prebuilt binaries with no
  install script. It must be kept current: image decoders are an attack surface.
- Image traffic passes through the site server and the API until a CDN exists (D1).
- Orphaned objects are possible after a failed commit; a sweep belongs with retention (D9).
- Hero and sharing images can reuse the library: a new section version with an image field
  needs no change to public serving.
